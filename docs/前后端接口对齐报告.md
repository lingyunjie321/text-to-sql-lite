## 一、全局总览

项目采用 **单 API 端点** 架构：前端通过 Next.js BFF 代理层将请求转发到后端 Python FastAPI。

```
浏览器 ──POST──▶ Next.js BFF (/api/v1/text-to-sql) ──POST──▶ FastAPI (/api/v1/text-to-sql)
```

**结论：核心查询链路已对齐，但存在 1 项高危差异和 4 项功能缺口。**

## 三、差异与问题详情

### 🔴 问题 1（高危）：请求体含后端不认识的字段

**文件**：
- 前端：`frontend/components/workbench/Workbench.tsx:118-124`
- 后端：`app/api/models.py:31`（`extra="forbid"`）

**现象**：当用户在设置页配置了模型或数据源后，Workbench 会构造带 `model_config` 和/或 `datasource_config` 的请求体发送给后端。后端 Pydantic 模型设置 `ConfigDict(extra="forbid")`，未声明的字段将触发 `RequestValidationError` → HTTP 422。

**触发条件**：
1. `model_config`：用户在设置页启用任意一个模型 tier（simple/standard/complex/fallback）
2. `datasource_config`：用户在设置页修改 `datasource_id` 为非 `"pagila"` 值，或用「表单模式」填写了连接信息

**影响**：配置了模型的用户无法正常查询，始终收到 422 错误。

**建议修复**：
- **方案 A**（临时）：前端在发送请求前剥离 `model_config` / `datasource_config`，仅在传递到 BFF 的同级 Next.js API route 中用（做 server-side env override）
- **方案 B**（长期）：后端扩展 `QueryRequest`，增加 `model_config` / `datasource_config` 可选字段并在请求级别支持动态模型路由和数据源配置

---

### 🟡 问题 2（中危）：设置页配置不生效

**文件**：
- 前端：`frontend/app/settings/page.tsx` + `ModelConfigSection` + `DatabaseConfigSection`
- `frontend/lib/model-config.ts`、`frontend/lib/datasource-config.ts`（纯 localStorage）

**现象**：前端有完整的设置 UI（模型配置、数据库连接配置），但仅存储在浏览器 localStorage，随请求发送时后端不识别（见问题 1）。这意味着设置页目前只是一个 **UI 演示**，实际配置不生效。

**模型路由实际行为**：后端通过 `.env` 中的环境变量 `LLM_*`、`LLM_SIMPLE_*`、`LLM_STANDARD_*`、`LLM_COMPLEX_*`、`LLM_FALLBACK_*` 等服务端配置决定模型路由，与前端设置无关。

**建议**：
- 短期：在设置页增加提示 "配置需在服务端环境变量中设置，前端配置仅用于本地调试"
- 长期：配合问题 1 方案 B，实现请求级模型覆盖

---

### 🟡 问题 3（低危）：扩展信息字段未实现

**文件**：
- 前端类型：`frontend/lib/types.ts:74-115`（`SchemaCandidate`, `SemanticReference`, `ComplexityRoute`, `RepairHistoryEntry`）
- 前端组件：`ReferenceInfo`、`SchemaCandidatesTable`、`SemanticReferencesGroup`、`ComplexityRoutePanel`、`RepairHistoryTimeline`
- 后端：整个工作流状态（`SQLTaskState`）中**确实有** schema linking、复杂度路由、修复历史等中间数据，但 `build_query_response()` 未将它们映射到响应中

**评估**：这些字段本质上后端工作流**已经计算了**（`candidate_tables`、`complexity_decision`、`repair_count` 等），只是没有映射到 JSON 响应中供前端展示。前端展示组件已写好，只需后端 `response.py` 增加字段映射。

**建议**：后端 `build_query_response()` 中增加这些字段的映射，充分利用已有数据提供更好的调试/透明度体验。

---

### 🟡 问题 4（低危）：鉴权不匹配

**文件**：
- 后端：`app/api/application.py:38-58`（HTTPBearer 鉴权，可选）
- 前端：`frontend/lib/api.ts`（无 Authorization header）

**现象**：后端支持通过 `TEXT_TO_SQL_API_KEY` 环境变量配置 API Key 鉴权。若配置了 API Key，前端所有请求将收到 401/403。

**影响**：当前 MVP 阶段默认不配置 API Key（`api_key_value is None` 时跳过鉴权），暂不影响。但若后续开启鉴权，前端需同步更新。

**建议**：在设置页增加 API Key 配置项，前端请求时携带 `Authorization: Bearer <key>` header。

---

**前端未使用** `GET /health`。可考虑在连接状态检测或设置页中调用，提供后端可达性反馈。

## 五、修复优先级建议

| 优先级 | 问题 | 影响 | 建议动作 |
|--------|------|------|----------|
| **P0** | 请求体 `model_config` / `datasource_config` 导致 422 | 配置模型的用户完全无法使用 | 前端剥离未实现字段，或后端扩展模型 |
| **P1** | 设置页配置不生效 | 用户困惑（配了没用） | 增加提示文案；长期实现请求级模型路由 |
| **P2** | 扩展信息字段未返回 | 参考信息面板空白 | `build_query_response()` 映射中间数据 |
| **P3** | API Key 鉴权不匹配 | 开启鉴权后前端无法请求 | 设置页增加 API Key 配置 + 请求带 Authorization |
| **P4** | Health 端点未对接 | 无后端可达性检测 | 可选优化 |
