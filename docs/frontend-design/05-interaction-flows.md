## 1. 主查询流程

### 1.1 状态机总览

```
                          ┌─────────────┐
                          │   IDLE      │  空闲态：等待用户输入
                          │ (初始/空闲)  │
                          └──────┬──────┘
                                 │ 用户提交问题
                                 ▼
                          ┌─────────────┐
                          │  LOADING    │  加载态：请求已发送，等待响应
                          └──────┬──────┘
                                 │ 收到响应 (HTTP 200)
                                 │ 解析 status 字段
                    ┌────────────┼────────────────────────────────┐
                    │            │            │            │       │
                    ▼            ▼            ▼            ▼       ▼
             ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌─────────┐ ┌─────────┐
             │ SUCCESS  │ │CLARIFY   │ │ FAILED   │ │ HTTP    │ │ NETWORK │
             │ (成功)   │ │ (需澄清)  │ │ (失败)    │ │ ERROR   │ │ ERROR   │
             │          │ │          │ │          │ │ (4xx/5xx)│ │ (无响应) │
             └────┬─────┘ └────┬─────┘ └────┬─────┘ └────┬────┘ └────┬────┘
                  │            │            │            │            │
                  │            │ 用户补充    │ 用户重试    │ 显示错误    │ 显示错误
                  │            │ → LOADING  │ → LOADING  │ → IDLE     │ → IDLE
                  │            │ 或跳过     │ 或修改     │            │
                  │            │ → IDLE    │ → IDLE    │            │
                  ▼            ▼            ▼            ▼            ▼
             ┌──────────┐                                          │
             │  IDLE    │◄─────────────────────────────────────────┘
             │ (可继续   │
             │  提问)    │
             └──────────┘
```

### 1.2 详细步骤

#### 步骤 1：IDLE → 用户输入

```
状态：IDLE
用户看到：
  - 底部输入区可交互
  - 提交按钮可用（或禁用，如果输入为空）
用户操作：
  - 在 Textarea 输入问题
  - 或点击示例问题 Chip 自动填入
系统反馈：
  - 输入框实时显示文字
  - 字符计数器更新（当前/2000）
  - 输入为空时提交按钮禁用；有内容时启用
前置校验（前端）：
  - 去首尾空白后长度 1-2000 字符
  - 超过 2000 字符：计数器变红，提交按钮禁用
  - 空白内容：提交按钮禁用
```

#### 步骤 2：提交 → LOADING

```
触发：用户点击提交按钮 或 按 Enter（非 Shift+Enter）
状态：IDLE → LOADING
系统行为：
  1. 在对话流区追加用户消息气泡（右对齐，显示问题文本）
  2. 在用户消息下方追加加载卡片（Spinner + "正在理解你的问题..."）
  3. 加载卡片下方显示 Skeleton 骨架屏（模拟表格形状）
  4. 输入框清空并禁用
  5. 提交按钮变为加载态（Spinner 替换图标，按钮禁用）
  6. 自动滚动到加载卡片位置
  7. 发起 POST /api/v1/text-to-sql 请求

请求体：
  {
    "question": "用户输入的问题文本（已去首尾空白）",
    "datasource_id": "pagila",
    "debug": false
  }

加载文案渐进式变化（可选增强）：
  - 0-3s：  "正在理解你的问题..."
  - 3-6s：  "正在生成 SQL 查询..."
  - 6-10s： "正在执行查询..."
  - 10s+：  "正在整理结果，请稍候..."
```

#### 步骤 3：收到响应 → 按 status 分支

```
状态：LOADING → 根据 status 分支
```

**分支 A：SUCCEEDED_FIRST_PASS / SUCCEEDED_REPAIRED**

```
条件：response.status === "SUCCEEDED_FIRST_PASS" || "SUCCEEDED_REPAIRED"
系统行为：
  1. 加载卡片替换为结果卡片
  2. 状态标签：
     - SUCCEEDED_FIRST_PASS → 绿色标签 "查询成功" + "一次通过"
     - SUCCEEDED_REPAIRED → 蓝色标签 "经修复后成功" + "经 N 次修复"
  3. 结果展示区：
     - 默认展示表格视图
     - 渲染 columns 为表头
     - 渲染 rows 为数据行
     - 前端分页（每页 50 行）
  4. 视图切换 Tab 出现：表格 / 柱状图 / 折线图（根据数据自动推荐）
  5. SQL 折叠区出现（默认折叠）
  6. 元信息折叠区出现（默认折叠）
  7. 截断提示（如 truncated=true）：表格上方显示警告条
  8. 导出 CSV 按钮出现
  9. 输入框重新可用
  10. 历史记录保存到 localStorage
  11. 自动滚动到结果卡片
状态：→ IDLE（可继续提问）
```

**分支 B：CLARIFICATION_REQUIRED**

```
条件：response.status === "CLARIFICATION_REQUIRED"
系统行为：
  1. 加载卡片替换为澄清卡片
  2. 状态标签：琥珀色 "需要补充信息"
  3. 展示澄清问题：response.clarification.question
  4. 出现补充输入框 + "提交补充" 按钮 + "跳过" 按钮
  5. 输入框重新可用（但建议用户先回应澄清）
  6. 自动滚动到澄清卡片
状态：→ CLARIFY_WAITING（等待用户补充）
详见：第 2 节 澄清流程
```

**分支 C：各种 FAILED_***

```
条件：response.status 以 "FAILED_" 开头 或 === "REJECTED_SECURITY"
系统行为：
  1. 加载卡片替换为错误卡片
  2. 状态标签：红色（FAILED_RESOURCE_RISK 为橙色）
  3. 展示友好错误文案（根据 status 映射，不直接展示 error.message）
  4. 根据错误类型显示操作按钮：
     - 可重试错误：显示 "重试" 按钮
     - 不可重试错误：显示 "修改问题" 按钮（聚焦输入框）
  5. 元信息折叠区出现（包含 error.error_type 和 error.code）
  6. 输入框重新可用
  7. 历史记录保存到 localStorage
  8. 自动滚动到错误卡片
状态：→ IDLE
详见：第 7 节 错误重试流程
```

**分支 D：HTTP 错误（非 200）**

```
条件：HTTP 状态码非 200（如 403, 422, 500）
系统行为：
  1. 加载卡片替换为错误卡片
  2. 根据 HTTP 状态码展示友好文案：
     - 403："您没有权限执行此操作"
     - 422："请求参数有误，请检查输入"
     - 500："系统遇到内部错误，请稍后重试"
  3. 显示 "重试" 按钮（500）或 "修改问题" 按钮（403/422）
  4. 输入框重新可用
状态：→ IDLE
```

**分支 E：网络错误**

```
条件：fetch 请求失败（网络中断、超时、CORS 等）
系统行为：
  1. 加载卡片替换为错误卡片
  2. 错误文案："网络连接失败，请检查网络后重试"
  3. 显示 "重试" 按钮
  4. 输入框重新可用
状态：→ IDLE
```

## 2. 澄清流程

### 2.1 状态机

```
                 ┌─────────────────────┐
                 │  CLARIFY_WAITING     │  收到 CLARIFICATION_REQUIRED
                 │  等待用户补充信息      │
                 └──────────┬──────────┘
                            │
              ┌─────────────┼─────────────┐
              │                           │
              ▼                           ▼
      ┌──────────────┐          ┌──────────────┐
      │ 用户提交补充  │          │ 用户点击跳过  │
      │ (SUBMIT)     │          │ (SKIP)       │
      └──────┬───────┘          └──────┬───────┘
             │                         │
             ▼                         ▼
      ┌──────────────┐          ┌──────────────┐
      │  LOADING     │          │  IDLE        │
      │  重新查询     │          │  回到空闲态   │
      └──────────────┘          └──────────────┘
```

### 2.2 详细步骤

#### 步骤 1：收到澄清请求

```
触发：response.status === "CLARIFICATION_REQUIRED"
状态：LOADING → CLARIFY_WAITING
系统行为：
  1. 加载卡片替换为澄清卡片
  2. 展示澄清问题：response.clarification.question
     示例："你的问题涉及'收入'，你想查询租金总额还是罚金总额？"
  3. 展示 clarification.code（仅在元信息折叠区，供调试）
  4. 出现补充输入框（Textarea，单行起，可扩展）
  5. 出现 "提交补充" 按钮（Primary）和 "跳过" 按钮（Ghost）
  6. 自动滚动到澄清卡片
  7. 聚焦补充输入框
```

#### 步骤 2A：用户提交补充

```
触发：用户在补充输入框输入内容，点击 "提交补充"
状态：CLARIFY_WAITING → LOADING
系统行为：
  1. 拼接新问题：
     原始问题 + "\n\n补充说明：" + 用户补充内容
     示例："各分类的平均租赁时长\n\n补充说明：我想查询实际租赁的天数"
  2. 在对话流追加用户补充消息气泡（右对齐，标注"补充说明"）
  3. 澄清卡片下方出现新的加载卡片
  4. 发起新的 POST /api/v1/text-to-sql 请求
  5. 后续流程同主查询流程步骤 2-3

请求体：
  {
    "question": "原始问题\n\n补充说明：用户补充内容",
    "datasource_id": "pagila",
    "debug": false
  }
```

#### 步骤 2B：用户点击跳过

```
触发：用户点击 "跳过" 按钮
状态：CLARIFY_WAITING → IDLE
系统行为：
  1. 澄清卡片保留在对话流中（不删除，作为历史记录）
  2. 在澄清卡片下方追加灰色提示："已跳过此澄清"
  3. 输入框聚焦，等待用户输入新问题
  4. 历史记录保存到 localStorage（标注为"已跳过澄清"）
```

### 2.3 澄清流程时序图

```
用户           前端              后端
  │              │                │
  │  提交问题     │                │
  │─────────────>│  POST 请求      │
  │              │───────────────>│
  │              │  CLARIFICATION │
  │              │  _REQUIRED     │
  │              │<───────────────│
  │              │                │
  │  展示澄清问题  │                │
  │<─────────────│                │
  │              │                │
  │  输入补充说明  │                │
  │─────────────>│                │
  │  点击提交补充  │                │
  │─────────────>│                │
  │              │  POST 请求      │
  │              │  (拼接后的问题)  │

## 3. 修复流程

### 3.1 概述

后端在 SQL 执行失败时可能自动修复（最多 3 次）。修复过程对用户完全透明，用户只在最终结果中看到修复信息。

### 3.2 修复结果的展示策略

修复流程不需要前端做额外交互，只需在结果展示时正确呈现修复信息：

```
状态：SUCCEEDED_REPAIRED
展示策略：弱化展示，不干扰用户
```

### 3.3 展示位置与方式

```
┌──────────────────────────────────────────────────────────┐
│ [✓ 经修复后成功]  经 2 次修复  ·  返回 10 行               │  ← 状态标签（蓝色，弱化）
├──────────────────────────────────────────────────────────┤
│  结果表格...                                               │
├──────────────────────────────────────────────────────────┤
│  ▸ 查看 SQL                                                │
├──────────────────────────────────────────────────────────┤
│  ▸ 详细信息                                                 │
│  ┌────────────────────────────────────────────────────┐  │  ← 展开后
│  │  Request ID:  xxx                                   │  │
│  │  Trace ID:    xxx                                   │  │
│  │  尝试次数:    3        ← attempts (repair_count+1)   │  │
│  │  修复次数:    2        ← repair_count                │  │
│  │  返回行数:    10                                    │  │
│  │  是否截断:    否                                     │  │
│  └────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────┘
```

### 3.4 展示规则

| 字段 | 展示位置 | 展示方式 |
|------|----------|----------|
| `status` | 状态标签 | 蓝色标签 "经修复后成功" |
| `repair_count` | 状态标签副文案 | "经 N 次修复" |
| `attempts` | 元信息折叠区 | "尝试次数: N"（= repair_count + 1） |
| `repair_count` | 元信息折叠区 | "修复次数: N" |

### 3.5 弱化原则

- **不弹 Toast**：修复成功不弹通知，避免打断用户
- **不高亮**：结果卡片不额外高亮修复信息
- **不展开 SQL**：SQL 折叠区仍默认折叠
- **元信息默认折叠**：attempts 和 repair_count 在折叠区内，需主动展开
- **仅在状态标签体现**：用户一眼看到"经修复后成功"即可，细节按需查看

### 3.6 修复失败（FAILED_REPAIR_EXHAUSTED）的处理

当修复次数耗尽仍未成功时，status 为 `FAILED_REPAIR_EXHAUSTED`：

```
┌──────────────────────────────────────────────────────────┐
│ [✕ 修复失败]  系统尝试修复但未能成功                        │
├──────────────────────────────────────────────────────────┤
│  ⚠ 系统多次尝试生成正确的 SQL 但未能成功                    │
│                                                         │
│  请尝试更清晰地描述你的问题，例如：                          │
│  · 明确指定要查询的表和字段                                │
│  · 提供更具体的时间范围或条件                               │
│  · 避免使用模糊的术语                                     │
│                                                         │
│                                          [修改问题]       │
├──────────────────────────────────────────────────────────┤
│  ▸ 详细信息                                               │
│  ┌────────────────────────────────────────────────────┐  │
│  │  尝试次数:    4        ← 达到上限                    │  │
│  │  修复次数:    3        ← 达到上限                    │  │
│  │  错误类型:    SYNTAX_ERROR / SCHEMA_ERROR / ...     │  │
│  └────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────┘
```

- 不可重试（建议修改问题）
- 展示 attempts=4 和 repair_count=3（均达上限）
- 展示 error.error_type（供技术排查）

## 4. 结果可视化切换

### 4.1 状态机

```
                 ┌──────────────────┐
                 │  TABLE_VIEW      │  默认：表格视图
                 │  (表格展示)       │
                 └────────┬─────────┘
                          │
              ┌───────────┼───────────┐
              │           │           │
              ▼           ▼           ▼
        ┌──────────┐ ┌──────────┐ ┌──────────┐
        │ BAR_CHART│ │LINE_CHART│ │ DISABLED │
        │ (柱状图)  │ │ (折线图)  │ │ (禁用)    │
        └────┬─────┘ └────┬─────┘ └──────────┘
             │            │
             │  点击 Tab 切换
             ▼            ▼
        ┌──────────────────────┐
        │  任意切换             │
        │  TABLE ↔ BAR ↔ LINE  │
        └──────────────────────┘
```

### 4.2 图表类型自动推荐逻辑

```
收到成功响应 (columns + rows)
         │
         ▼
    ┌────────────┐
    │ 列数判断    │
    └─────┬──────┘
          │
          ├─ 列数 > 2
          │    → 图表 Tab 禁用
          │    → 仅展示表格
          │    → 提示："当前结果列数较多，不适合图表展示"
          │
          ├─ 列数 == 2
          │    │
          │    ▼
          │   ┌────────────────┐
          │   │ 第1列类型判断    │
          │   └───────┬────────┘
          │           │
          │           ├─ 第1列为日期/时间（含 date/time/timestamp）
          │           │    → 推荐：折线图（默认选中）
          │           │    → 可用：表格、折线图、柱状图
          │           │
          │           ├─ 行数 ≤ 10
          │           │    → 推荐：柱状图（默认选中）
          │           │    → 可用：表格、柱状图、折线图
          │           │
          │           └─ 行数 > 10
          │                → 推荐：柱状图（默认选中）
          │                → 可用：表格、柱状图、折线图
          │
          └─ 列数 == 1
               → 图表 Tab 禁用
               → 仅展示表格
```

### 4.3 详细步骤

#### 步骤 1：默认进入表格视图

```
触发：收到 SUCCEEDED_FIRST_PASS / SUCCEEDED_REPAIRED 响应
状态：→ TABLE_VIEW
系统行为：
  1. 结果展示区默认渲染表格
  2. Tab 栏：[📋 表格(选中)] [📊 柱状图] [📈 折线图]
  3. 根据自动推荐逻辑决定图表 Tab 是否可用
```

#### 步骤 2：切换到柱状图

```
触发：用户点击 "柱状图" Tab
状态：TABLE_VIEW → BAR_CHART
系统行为：
  1. 表格视图淡出，柱状图视图淡入（200ms 过渡）
  2. Tab 高亮切换到 "柱状图"
  3. 渲染 Recharts <BarChart>:
     - X 轴：第 1 列数据（通常是分类/名称）
     - Y 轴：第 2 列数据（数值）
     - 柱体颜色：主色 #6366f1
     - 高度：400px（桌面）/ 300px（移动端）
  4. 鼠标悬停柱体显示 Tooltip（列名 + 数值）
  5. 图例显示在底部

## 5. 历史记录流程

### 5.1 数据结构

```typescript
interface HistoryRecord {
  id: string;              // 唯一标识（使用 request_id 或生成 UUID）
  timestamp: number;       // 时间戳（毫秒）
  question: string;        // 用户问题
  response: QueryResponse;  // 完整响应（序列化为 JSON）
  conversationIndex: number;// 对话轮次序号
}

interface Conversation {
  id: string;              // 对话 ID
  createdAt: number;       // 创建时间
  updatedAt: number;       // 最后更新时间
  title: string;           // 对话标题（取第一条问题的摘要）
  records: HistoryRecord[];// 所有轮次记录
}
```

### 5.2 存取流程

#### 保存到 localStorage

```
触发：每次查询完成（成功/失败/澄清），自动保存
状态：查询完成 → 自动保存
系统行为：
  1. 将当前对话的所有记录序列化为 JSON
  2. 写入 localStorage，key = "text-to-sql-history"
  3. 存储结构：Conversation[]
  4. 最多保留 50 条对话（超出时删除最早的）
  5. 单条对话最多保留 100 轮记录（超出时截断早期记录）

保存时机：
  - SUCCEEDED_FIRST_PASS / SUCCEEDED_REPAIRED → 保存
  - CLARIFICATION_REQUIRED → 保存（标注澄清状态）
  - 各种 FAILED_* → 保存（标注错误状态）
  - 用户跳过澄清 → 更新该记录状态
```

#### 从 localStorage 读取

```
触发：进入历史记录页 / 恢复对话
系统行为：
  1. 从 localStorage 读取 "text-to-sql-history"
  2. JSON.parse 反序列化
  3. 按 updatedAt 降序排列（最近优先）
  4. 如果解析失败（数据损坏）：清空 localStorage，显示空状态
```

### 5.4 恢复对话流程

```
触发：用户在历史记录页点击某条记录的"查看"按钮
状态：历史记录页 → 首页
系统行为：
  1. 读取该对话的完整 records 数组
  2. 跳转到首页 /?conversation={conversationId}
  3. 首页加载时检查 URL 参数
  4. 如果有 conversationId：
     a. 从 localStorage 读取该对话
     b. 恢复对话流：依次渲染所有历史记录（用户消息 + 结果卡片）
     c. 滚动到最后一条记录
     d. 输入框聚焦，可继续提问
  5. 如果没有 conversationId：
     a. 显示空状态（欢迎区 + 示例问题）
```

### 5.5 localStorage 容量管理

```
策略：
  1. 单条对话估算大小：约 5-50KB（取决于结果行数）
  2. localStorage 限制：约 5-10MB
  3. 保留策略：
     - 最多 50 条对话
     - 单条对话最多 100 轮
     - 超出时删除最早的对话
  4. 写入失败处理（空间不足）：
     - 删除最早的 5 条对话
     - 重试写入
     - 仍失败则提示用户清理历史
```

## 附录：全局状态管理建议

### 推荐方案：React Context + useReducer

```typescript
// 全局状态结构
interface AppState {
  conversations: Conversation[];    // 所有对话
  currentConversationId: string | null;  // 当前对话 ID
  queryStatus: QueryStatus;         // 当前查询状态
  currentResult: QueryResponse | null;   // 当前查询结果
}

type QueryStatus =
  | { type: 'IDLE' }
  | { type: 'LOADING' }
  | { type: 'SUCCESS'; response: QueryResponse }
  | { type: 'CLARIFY_WAITING'; response: QueryResponse }
  | { type: 'ERROR'; response: QueryResponse | null; httpStatus?: number; networkError?: boolean };
```

### 不使用全局状态库的理由

- 应用状态相对简单，主要是当前对话流 + 查询状态
- React Context + useReducer 足以覆盖
- 历史记录通过 localStorage 持久化，不需要全局状态管理
- 避免引入 Redux/Zustand 等额外依赖，保持轻量

### BFF 代理路由（Route Handler）

```typescript
// src/app/api/v1/text-to-sql/route.ts
import { NextRequest, NextResponse } from 'next/server';

const BACKEND_URL = process.env.BACKEND_URL || 'http://127.0.0.1:8000';
const API_KEY = process.env.API_KEY;  // 后端 API Key，从环境变量注入

export async function POST(request: NextRequest) {
  const body = await request.json();

  const response = await fetch(`${BACKEND_URL}/api/v1/text-to-sql`, {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      ...(API_KEY && { Authorization: `Bearer ${API_KEY}` }),
    },
    body: JSON.stringify(body),
  });

  const data = await response.json();
  return NextResponse.json(data, { status: response.status });
}
```

> **注意**：不要在 Route Handler 中加 `export const runtime = "nodejs"`，默认就是 Node.js runtime。不要加 `export const dynamic = "force-dynamic"`，POST 请求本身就是动态的。
